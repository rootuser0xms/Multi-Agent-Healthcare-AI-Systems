# Healthcare Multi-Agent System with PHI Leakage Evaluation

A three-agent healthcare AI pipeline (research lookup, patient/insurance history, imaging + diagnosis + booking), evaluated for internal-channel PHI leakage using a methodology adapted from **AgentLeak** (El Yagoubi et al., 2026). This repository accompanies the paper.

**Headline result:** across 80 test scenarios (20 synthetic patients × 4 imaging modalities), a purpose-scoped PHI sanitization layer reduced internal-channel data leakage from **100% to 0%** on both the final-output channel and the inter-agent message channel, compared to a naive baseline with no sanitization. This result is exact and statistically tested — Clopper-Pearson 95% CI [0.00%, 4.51%] (sanitized) vs. [95.49%, 100.00%] (naive), Fisher's exact test p = 2.17×10⁻⁴⁷ — not just a point estimate.

---

## ⚠️ Data Disclosure

**All patient data in this project is synthetic**, generated with the [Faker](https://faker.readthedocs.io/) library — no real patient records, real names, or real medical data are used anywhere in this repository. Imaging data is drawn from public, de-identified sources (see [Data Sources](#data-sources) below).

## Architecture

```
                        ┌───────────────────────┐
                        │      Orchestrator     │
                        │ (routes tasks, scopes │
                        │ what each agent sees) │
                        └───────────┬───────────┘
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
   ┌───────────────────┐ ┌────────────────────┐ ┌─────────────────────────┐
   │ Agent 1: Research │ │ Agent 2: Patient   │ │   Agent 3: Imaging +    │
   │ (live PubMed API) │ │ History/Insurance  │ │   Diagnosis + Booking   │
   │                   │ │ (PHI-sanitized,    │ │   (MedGemma 1.5 4B-it + │
   │                   │ │  purpose-scoped)   │ │    escalation logic)    │
   └───────────────────┘ └────────────────────┘ └─────────────────────────┘
```

See `data/figures/fig1_architecture.png` for the rendered diagram (regenerable — see [Reproducing the Paper's Figures and Tables](#reproducing-the-papers-figures-and-tables)).

- **Agent 1 (Research)** — queries PubMed's live E-utilities API, restricted to human-subject studies via a `humans[MeSH Terms]` filter. Only invoked when a case is flagged for human review, using the specific clinical term that triggered the flag.
- **Agent 2 (Patient/Insurance)** — looks up synthetic patient records, returning a field set scoped to the calling purpose (`booking`, `insurance_verification`, `full_clinical`) via `tools/phi_sanitizer.py`.
- **Agent 3 (Imaging)** — runs `google/medgemma-1.5-4b-it` on a medical image, extracts a finding and an urgency rating, then routes the case or flags it for human review based on modality-specific clinical keyword detection with sentence-scope negation handling (NegEx-style; Chapman et al., 2001).
- **Orchestrator** — coordinates the full patient-visit flow and logs every inter-agent handoff via `tools/audit_log.py`.

## Reproducing the Results

### Verify each agent individually

```bash
python -m agents.research_agent
python -m agents.patient_agent
python -m agents.imaging_agent
python -m agents.orchestrator
```

### Run the full AgentLeak-style security evaluation

```bash
caffeinate -i python -m tools.agentleak_eval 
```

Runs 20 synthetic patients through all 4 imaging modalities, once through the sanitized pipeline and once through the naive baseline, reporting leakage on:

- **C1 (final output)** — does the report returned to the user contain PHI beyond a bare patient ID?
- **C2 (inter-agent messages)** — does any logged handoff between agents contain PHI beyond what that handoff needs?

Results save to `results/agentleak_eval_sanitized_all_modalities.json` and `..._naive_all_modalities.json`.

**Runtime note:** MedGemma inference runs on CPU by default (see [Hardware Notes](#hardware-notes)) — the full evaluation involves ~320 model calls and can take several hours.

### Reproducing the Paper's Figures and Tables

Every figure and every numeric table value in the paper is regenerable directly from the raw audit log — nothing is hand-entered:

```bash
python tools/generate_paper_artifacts.py
```

This resolves paths relative to its own location (project root's `data/` folder is assumed to be a sibling of `tools/`), reads `data/audit_log.jsonl`, and writes:
- `data/figures/fig1_architecture.png`, `fig2_flowchart.png`, `fig3_leakage_comparison.png`, `fig4_sequence.png`
- `data/tables.json` — every number in Tables I–IV, machine-checkable against the paper

If you don't have a real `audit_log.jsonl` yet, re-run the agents/evaluation above first to generate one — the script will otherwise fall back to placeholder timing values in Figure 4 and print a warning.

## Results Summary

| Metric | Sanitized | Naive |
|---|---|---|
| C1 (final output) leak rate, pooled (n=80) | 0% | 100% |
| C2 (inter-agent) leak rate, pooled (n=80) | 0% | 100% |
| Exact 95% CI | [0.00%, 4.51%] | [95.49%, 100.00%] |

Fisher's exact test on the sanitized-vs-naive comparison: **p = 2.17×10⁻⁴⁷**.

Additional results (full detail in the paper):
- **Weighted blast radius** reduced by 76.2% (booking scope) relative to full-record access
- **Sanitization computational overhead**: 2.9 ms mean, vs. 19.2 s mean for MedGemma inference — under 0.02% of total visit latency
- **Escalation logic** (30-case labeled test set): F1 improved from 0.682 (naive keyword matching) → 0.909 (fixed-window negation) → 1.000 (sentence-scope NegEx)

## Hardware Notes

- **Apple Silicon (MPS) is not currently supported for MedGemma 1.5 in this repo** — loading with `device_map="mps"` caused a hard segmentation fault during weight loading in testing. `tools/medgemma_tool.py` defaults to CPU (`float32`).
- A CUDA GPU is recommended if available; set `MEDGEMMA_DEVICE=cuda` to use it.

## Known Limitations

- The security evaluation covers 2 of AgentLeak's 7 defined leakage channels (C1: final output, C2: inter-agent messages) — the two reported as most significant in the source benchmark.
- Booking tool's clinical keyword detection is a simplified NegEx-style adaptation, not a validated clinical NLP model.
- Patient data is entirely synthetic structured records — sanitization has not been tested against PHI embedded in unstructured free-text clinical narrative.
- MedGemma 1.5's imaging findings were not evaluated against ground-truth diagnostic labels or expert review; this project evaluates privacy leakage and escalation-logic behavior, not diagnostic accuracy.
- Blast-radius sensitivity weights are author-defined for this analysis, not drawn from an external validated standard.
- This is a research prototype, not a validated clinical tool, and must not be used for real patient care.

## Methodological Note

During development, an initial version of the leakage evaluation harness scanned the entire cumulative audit log by patient ID only, with no scoping to the current evaluation run. Since patient IDs are reused across test runs, this caused the sanitized pipeline's leakage check to occasionally register genuinely-leaky entries written by the naive pipeline for the same patient ID, producing false-positive leak detections. This was caught via repeated-run comparison before any results were finalized, and fixed by scoping leakage checks to log entries timestamped at or after the start of the specific evaluation run (`tools/agentleak_eval.py`, `check_inter_agent_leakage()`). Documented here for transparency and reproducibility.
